# ADR-0015: Error handling style

- **Decision:** D-15 (SPEC §2.1)
- **Status:** Accepted (2026, Cairn 1.x)
- **Category:** Architecture

## Context

Stable error codes are a cross-layer contract in Cairn. They are (a) the contract for §14 tests —
the code set is checked 1:1 against `crates/cairn-core/src/error.rs` by
`scripts/lint-docs.sh --check-codes`, **153 codes** (§16.1); (b) model-visible recovery guidance —
every tool error returns `ok:false`, `error.code`, `error.message`, `error.recovery` without
aborting the turn (§16.4); and (c) user-visible format — every error shows a stable code line plus
a `recovery`/hint line (REQ-TUI-010, §10.9), and every non-zero exit prints at least one line with
the stable code (REQ-CLI-002, §11.2). Logs carry the same `code` field (§12.1).

Library crates must not leak their error style into the binary, and panics are not an error path.

## Decision

**`thiserror` for library crates, `anyhow` only in the binary crate; all user-facing errors carry a
stable code (`E-XXX-YYY`), with `W-*` for non-fatal warnings** (versions frozen at M0, §15.2).
Per the spec's rationale: the codes are the contract for §14 tests and for model-visible recovery
guidance.

## Alternatives rejected

| Alternative | Why it was rejected |
|-------------|---------------------|
| `eyre` | Not chosen; the spec selects `thiserror`/`anyhow` (no separate rationale recorded in SPEC §2.1 beyond the choice's rationale that codes are the contract). |
| Panics | Not chosen; every error path must be code-carrying and observable — §14.3.2b requires model-visible *and* user-visible behavior for every code, which a panic cannot provide. |

## Consequences

- Positive: one code space spans tools (§6.2), providers (§4.5), config (§11.4.2), sessions (§11.7) and checkpoints (§9.8) without being defined twice — partitioned by domain (§16.3).
- Positive: drift between spec and code is mechanically prevented (`scripts/lint-docs.sh --check-codes`, §16.1), and M0 delivers the registry itself (§15.4).
- Risks / costs: every new user-facing error needs a spec row and a coverage row (§14.3.2b) — documentation and code must move together or CI fails.
- Risks / costs: the interim `E-IMPL-STAGE` code (exit 1, §11.2) exists only while milestones are outstanding and MUST shrink with each release; it must never mask a subsystem's own code once that subsystem ships.
