# ADR-0001: Language & runtime

- **Decision:** D-01 (SPEC §2.1)
- **Status:** Accepted (2026, Cairn 1.x)
- **Category:** Technology

## Context

Cairn is a terminal-native agent: it must start instantly, ship as one self-contained binary on
every Tier 1 platform (Linux x86_64 glibc + musl, macOS arm64/x86_64 — REQ-PROD-001, §1.4), and keep
a 60 fps render loop alive while streaming provider output and parsing/indexing repositories.

The budgets this decision must satisfy are explicit in the spec. §2.2 (derived from D-01) caps the
stripped static musl binary at ≤ 18 MB, `cairn --version` at ≤ 40 ms, cold start to first TUI frame
at ≤ 150 ms (P95), warm start at ≤ 80 ms (P95), and peak idle TUI RSS at ≤ 120 MB. §13 restates
these as P-01, P-02, P-03, P-20 and P-26 and adds the reliability ceilings (REQ-PERF-002 idle
thread count, REQ-PERF-003 every wait has a timeout). What is pinned is the *minimum* supported
Rust version — `Cargo.toml` `rust-version = "1.83"` — while `rust-toolchain.toml` asks for
`stable` (+ rustfmt, clippy) so developers and the 3-OS CI matrix (§15.1, §15.3) build with a
current stable. The toolchain file deliberately does *not* say `1.83`: cargo 1.83 cannot parse the
`edition2024` manifests in the dependency graph, and its resolver cannot skip them, so a pinned
1.83 toolchain would not even resolve the lockfile. The MSRV is therefore enforced by
`.cargo/config.toml` (`resolver.incompatible-rust-versions = "fallback"`, which keeps `Cargo.lock`
buildable at 1.83) and by a dedicated `msrv` CI job running `cargo +1.83.0 check --workspace
--all-targets` and `cargo +1.83.0 test --workspace`.

## Decision

Cairn is written in **Rust, 2021 edition, with MSRV 1.83** (`rust-version = "1.83"` in every
`Cargo.toml`), built on whatever `rust-toolchain.toml` selects — `stable` today. The spec's
rationale for the language choice: a static musl binary of ~14 MB (against the ≤ 18 MB budget),
startup-to-first-frame within the startup budget, fearless concurrency for the event bus, and
`tokio` giving structured async + cancellation. The spec adds that Go was rejected for GC and
weaker `os/exec` PTY ergonomics, and Node for a 300 ms+ startup and a runtime dependency.

## Alternatives rejected

| Alternative | Why it was rejected |
|-------------|---------------------|
| Go | Larger binaries with GC pauses, weaker pattern matching for parsers; GC and `os/exec` PTY ergonomics are weaker. |
| TypeScript/Node | 100 MB+ runtime and slow cold start; Node startup 300 ms+ and a required runtime dependency. |
| Python | Packaging nightmare. |

## Consequences

- Positive: one static musl/gnu binary with no runtime dependency satisfies REQ-PROD-001 Tier 1 shipping (Linux gnu + musl, macOS arm64 + x86_64).
- Positive: no GC pauses plus fearless concurrency underpin the typed event bus (§3.5) and the ≥ 45 fps streaming frame budget (P-06).
- Risks / costs: the §2.2 budgets are normative (REQ-TECH-001) and gated in CI by the perf tier (T-PERF-001, T-PERF-010) — binary-size or startup regressions fail the nightly perf job.
- Risks / costs: `rust-toolchain.toml` asks for `stable`, so the *building* toolchain floats forward on every rustup update — new clippy lints or rustfmt output are possible, and it is the CI gate that catches them, not the developer's machine. The frozen part is the MSRV: raising 1.83 is a deliberate workspace-level change touching `rust-version`, `.cargo/config.toml` and the `msrv` CI job, not a per-developer choice.
