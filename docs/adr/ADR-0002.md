# ADR-0002: Concurrency model

- **Decision:** D-02 (SPEC §2.1)
- **Status:** Accepted (2026, Cairn 1.x)
- **Category:** Architecture

## Context

Cairn runs a main-thread TUI event loop (60 fps cap), a Tokio runtime (4 workers by default,
`CAIRN_RT_THREADS`) for async tasks, a Rayon pool (≤ 8) for CPU-bound jobs, and a dedicated
`blocking` pool (2 threads) for keychain and SQLite calls (§3.3). All cross-module communication
for observable behavior must flow through the event bus or an explicit trait (REQ-ARCH-003); the
bus has a lag drop policy that never drops critical events (REQ-ARCH-005); and every send must be
cancellable, with no blocking sends outside Rayon jobs (REQ-ARCH-006).

Cancellation is a first-class UX contract: Esc/Ctrl+C/SIGTERM semantics are tabled in §8.6, a
cancelled parent must cancel all descendants within 10 ms (REQ-ARCH-007), and process exit must
cancel the root token, flush the session within 500 ms, then `_exit` — exit code 13 if the flush
fails (REQ-ARCH-008). Session state is touched concurrently by the turn loop, the session writer
and tool tasks, so races must be structurally impossible rather than merely unlikely.

## Decision

**`tokio` multi-thread runtime + actor-style tasks communicating over typed `mpsc` channels, with
one `CancellationToken` tree.** Per the spec's rationale: structured cancellation maps directly to
Ctrl+C semantics (§8.6), and actors avoid data races on session state. The tree is rooted at a
process token; a turn token per user turn carries tool-call, model-stream and subagent tokens, and
background jobs hang off their own token (§3.3). Channels are typed (`cmd`, `evt`, `tool`,
`delta`, `job`) with fixed capacities, a broadcast bus, and a critical priority lane (§3.3).

## Alternatives rejected

| Alternative | Why it was rejected |
|-------------|---------------------|
| Green threads à la Erlang | No separate rationale recorded in SPEC §2.1; the choice's own rationale (structured cancellation, race-free session state) is the basis of the decision. |
| `async-std` | No separate rationale recorded in SPEC §2.1; Tokio is the runtime the rest of the spec builds on (§3.3, §3.4, §15.2). |
| Lock-heavy shared state | Rejected: shared mutable state is hard to reason about when reconstructing an in-flight turn. |

## Consequences

- Positive: one cancellation tree gives uniform Esc/Ctrl+C/SIGTERM behavior with the ≤ 10 ms propagation budget (REQ-ARCH-007, T-ARCH-007).
- Positive: actor-style tasks plus typed channels make session-state data races structurally impossible, and let the bus drop only idempotent `ToolProgress` events under lag (REQ-ARCH-005, T-ARCH-005).
- Risks / costs: the channel design is constrained — every send must stay cancellable and no blocking send may exist outside Rayon jobs (REQ-ARCH-006, T-ARCH-006).
- Risks / costs: multi-actor wiring must still meet the shutdown contract — cancel the root token, ≤ 500 ms session flush, exit 13 on failure (REQ-ARCH-008, T-ARCH-008).
