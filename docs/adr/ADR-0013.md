# ADR-0013: Dependency policy

- **Decision:** D-13 (SPEC §2.1)
- **Status:** Accepted (2026, Cairn 1.x)
- **Category:** Process

## Context

Cairn ships as a distributed binary (D-14: Apache-2.0 source available, commercial license sold
separately), so the spec requires that the dependency tree stays "proprietary-compatible" — copyleft
in any linking position is unacceptable, with **no exceptions** (§2.1 D-13 rationale). The rule has
to be machine-enforced, not reviewed by hand: `deny.toml` sits at the workspace root (§15.1) and
REQ-TECH-002 states that `cargo deny check licenses` MUST pass in CI with the D-13 allow-list, and
that a new dependency with a non-allow-listed license MUST fail the build. This is also a release
risk (R8, §15.5: dependency license/audit failure blocks release) mitigated by running `cargo-deny`
on every PR.

## Decision

**Permissive licenses only: MIT, Apache-2.0, BSD-2/3, ISC, Unlicense, Zlib, Unicode-3.0. MIT-0
accepted. Exception: none.** Enforcement is `cargo-deny` via `deny.toml` (licenses, bans, sources —
§15.1) in CI, exactly as REQ-TECH-002 requires. The spec notes `Unicode-3.0` was added because
`unicode-ident` (via `proc-macro2`/`syn` → clap, schemars) needs it as `(MIT OR Apache-2.0) AND
Unicode-3.0`, and that D-13 exists to reject copyleft, not permissives (§16.5).

## Alternatives rejected

| Alternative | Why it was rejected |
|-------------|---------------------|
| GPL-2.0 | Copyleft in any linking position is rejected by `cargo-deny`; the binary is distributed under a proprietary-compatible license. |
| LGPL | Same: copyleft linkage is rejected; exception: none. |
| MPL | Same: copyleft in any linking position is rejected. |
| SSPL | Same: copyleft in any linking position is rejected. |
| AGPL | Same: copyleft in any linking position is rejected. |

## Consequences

- Positive: the rule is enforced automatically — T-TECH-001 adds a GPL-2.0 crate in a branch and asserts `cargo deny check licenses` fails (REQ-TECH-002).
- Positive: a small, permissive-only dependency set keeps the audit surface small (risk R8 mitigation, §15.5).
- Risks / costs: any needed dependency outside the allow-list cannot be added at all (exceptions: none) — it must be replaced or reimplemented, which can block a feature or delay a release (R8).
