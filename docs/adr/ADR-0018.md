# ADR-0018: Secrets at rest

- **Decision:** D-18 (SPEC §2.1)
- **Status:** Accepted (2026, Cairn 1.x)
- **Category:** Architecture

## Context

Provider API keys must be usable and never leak. §4.10 fixes the credential lookup order (first
hit wins): 1) `CAIRN_<PROVIDER>_API_KEY` env, 2) provider-standard env (`ANTHROPIC_API_KEY`,
`OPENAI_API_KEY`, `OLLAMA_API_KEY`), 3) OS keychain entry `service=cairn`, `account=<provider>`,
4) `~/.config/cairn/config.toml` under `providers.<id>.api_key`, 5) workspace-local
`.cairn/credentials.toml` (gitignored by `cairn init`). Around that, REQ-PROV-015..019 require
`0600` file permissions (warn `W-CRED-PERM` on `0644`), redaction of key material in logs, events,
sessions, traces and model context (REQ-PROV-016), `cairn auth login` preferring the keychain with
an explicit confirmation prompt on fallback (REQ-PROV-017), `cairn auth list` showing key source
and last 4 characters only (REQ-PROV-018), and no key ever sent to another provider
(REQ-PROV-019).

§9.6 complements storage with redaction-before-write: 12 pattern families including pattern 10 —
the active provider key values, loaded at startup, replaced with `***REDACTED***` — applied before
bytes reach any sink (REQ-SAFE-010, REQ-SAFE-011). §9.9's threat model carries the related rows:
credentials in logs → redact-before-write + last-4 display (T-OPS-006), and session files at rest
→ `0600` (T-SESS-031).

## Decision

Store secrets in the **OS keychain via the `keyring` crate** (Secret Service / Keychain / Windows
Credential Manager), **falling back to the config file with `0600`** — and the fallback explicitly
warns. Per the spec's rationale: the keychain is the only option with consistent cross-platform
support; the fallback explicitly warns. The storage choice plugs into the §4.10 lookup order above.

## Alternatives rejected

| Alternative | Why it was rejected |
|-------------|---------------------|
| Plain config | Not chosen as the primary store; the keychain provides protection the plain file cannot (the spec keeps the config file only as an explicitly-warning fallback). |
| `age` encryption | Rejected: the keychain is the only option with consistent cross-platform support. |

## Consequences

- Positive: one consistent store across Tier 1/2 platforms (Linux Secret Service, macOS Keychain, Windows Credential Manager), with env-var layers preserving scripted/CI usage (persona P5, §4.10 lookup steps 1–2).
- Positive: defense in depth — even when a key must live in a file, it is `0600` (REQ-PROV-015) and every sink passes through the redactor (REQ-PROV-016, REQ-SAFE-010, §9.6 pattern 10).
- Risks / costs: keychain availability varies by environment, so the fallback path is always present — it must warn, confirm on `cairn auth login` (REQ-PROV-017) and chmod `0600` with `W-CRED-PERM` (REQ-PROV-015).
- Risks / costs: keyring calls are blocking, so they are confined to the dedicated 2-thread blocking pool (§3.3), constraining where credentials may be read.
