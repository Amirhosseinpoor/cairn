# ADR-0005: Retry & backoff

- **Decision:** D-05 (SPEC §2.1)
- **Status:** Accepted (2026, Cairn 1.x)
- **Category:** Architecture

## Context

Provider calls fail in many ways and Cairn must distinguish transient from permanent failures
(§4.5 error taxonomy): 401/403/404/TLS/4xx are terminal, while 408, 429, 5xx, DNS/connect and
mid-stream idle timeouts are retryable. Retries must be bounded twice over — by attempt count (max
5) and by a total per-call time budget of 180 s (`providers.max_total_ms`, REQ-PROV-005) — and must
obey cancellation: all retries stop within 50 ms of `token.cancel()` (REQ-PROV-006).

Concurrent sessions hitting the same provider at once create a thundering-herd risk, and 429
responses carry `Retry-After` (seconds or HTTP-date) that must be honored. Tool execution retries
are a separate concern and are never automatic (except one `web_fetch` retry on connection reset,
§4.5).

## Decision

**Exponential backoff: base 500 ms, factor 2.0, max 30 s, full jitter, max 5 attempts for
429/5xx/network; 0 attempts for 4xx except 408/429.** The normative matrix lives in §4.5, with
`delay_n = rand_uniform(0, min(30000, 500 * 2^(n-1)))` ms for n = 1..5; `E-PROV-RATELIMIT` uses
`max(delay_n, retry_after_ms)` capped at 120000 ms. Per the spec's rationale: full jitter
(`rand(0, min(cap, base*2^n))`) minimizes thundering herds across concurrent sessions.

## Alternatives rejected

| Alternative | Why it was rejected |
|-------------|---------------------|
| Fixed interval | Not chosen; the spec selects exponential backoff with full jitter (no separate rationale recorded in SPEC §2.1). |
| Decorrelated jitter | Not chosen; full jitter is the spec's stated means of minimizing thundering herds across concurrent sessions. |

## Consequences

- Positive: full jitter spreads concurrent sessions apart, and the closed-form delay makes waits exactly assertable (T-PROV-005: `Retry-After: 7` → wait ≥ 7 s, ≤ 7.5 s, 5 attempts, then `E-PROV-RATELIMIT`).
- Positive: non-retryable classes fail fast with actionable messages (`E-PROV-AUTH` → `cairn auth login <id>`), keeping bad credentials out of the retry loop (§4.5).
- Risks / costs: a flaky network consumes the whole budget before Cairn reports failure — retries are capped at 180 s per model call (REQ-PROV-005), after which the turn ends provider-fatal (exit 3, §11.2).
- Risks / costs: the backoff must remain cancellable within 50 ms (REQ-PROV-006, T-PROV-006), so sleeps cannot be naive.
