# ADR-0016: Serialization

- **Decision:** D-16 (SPEC §2.1)
- **Status:** Accepted (2026, Cairn 1.x)
- **Category:** Technology

## Context

The spec treats generated schemas as the parity mechanism between spec and code: event JSON
Schemas in `schemas/events/*.schema.json` are generated from Rust types and CI verifies the
generation is up to date (REQ-ARCH-009, T-SCHEMA-002); event payload versions are additive within
1.x, with a `v` bump required to remove or rename a field (REQ-ARCH-010, T-SCHEMA-003); the config
schema at `schemas/config.schema.json` is emitted from the same Rust structs and must carry
`default`, `enum`, `pattern` and `x-env-var`/`x-flag`/`x-config-key` annotations for every §11.1
flag (§11.4.3, REQ-ARCH-011, T-CFG-001). The same types also serialize session JSONL (snake_case,
§4.1), the model registry (§4.9) and `--output json`/`stream-json` event envelopes (§3.5).

## Decision

Use **`serde` + `serde_json`, with JSON Schema emitted via `schemars` 0.8** (frozen at M0,
§15.2). Per the spec's rationale: the schemas in §6 (and the event/config schemas) are generated
from the same Rust types, guaranteeing spec/code parity (test T-SCHEMA-001).

## Alternatives rejected

| Alternative | Why it was rejected |
|-------------|---------------------|
| `rkyv` | Not chosen; the spec's rationale is that schemas must be generated from the same Rust types for spec/code parity (no separate rationale recorded in SPEC §2.1). |
| Manual serialization | Same: hand-written encoders cannot guarantee spec/code parity (T-SCHEMA-001 would have nothing to diff against). |

## Consequences

- Positive: one source of truth — tool, event and config schemas are regenerated from Rust types and diffed in CI (`scripts/check-schemas.sh [--write]`, which runs the `dump_schema` / `dump_event_schemas` generators, §15.3; T-SCHEMA-001, T-SCHEMA-002).
- Positive: schema evolution is gated — an incompatible payload change fails CI until `v` is bumped and a migration note is added (REQ-ARCH-010, T-SCHEMA-003).
- Risks / costs: generated files must be regenerated whenever types change, or CI fails on drift (T-SCHEMA-002) — contributors carry a regeneration step in their workflow.
- Risks / costs: within 1.x, event payloads must stay additive; removing or renaming a field forces an envelope `v` bump plus a §11.7 migration note.
